# Bonnes pratiques détectées

- **Capteurs Pi** : chemins hwmon numérotés de façon instable, les chercher par le fichier `name` (`pwmfan`, `cpu_thermal`) et redétecter après un échec de lecture.
- **Ventilateur** : `pwm1` et `fan1_input` peuvent valoir 0 alors qu'il tourne ; croiser avec `cooling_device*/cur_state`.
- **Collecte** : thread séparé de l'UI ; un capteur en échec donne `None` (et un panic est rattrapé par `catch_unwind`), jamais un arrêt de la collecte. Donc pas de `panic = "abort"` en release.
- **Fichiers non versionnés** : `target/`, captures d'écran et `.DS_Store` ignorés par git.
- **Throttling Pi** : lire `get_throttled` en sysfs (`devices/platform/*/get_throttled`) avant de lancer `vcgencmd` ; le fallback `vcgencmd` n'est tenté que sur le vrai `/sys` pour que les tests ne dépendent pas de la machine.
- **Consommation Pi 5** : `vcgencmd pmic_read_adc` (lecture seule, sans sudo) ; appariement des rails `_A`/`_V` par nom, `EXT5V_V` exclu car sans courant. Comme le throttling, appelé seulement sur le vrai `/sys`.
- **Graphiques / échelle auto** : une courbe pleine (aires) sur une échelle automatique exagère les valeurs (47 °C paraît « presque plein ») ; préférer une ligne.
- **Lignes compactes** : une ligne binaire (throttling) n'a pas besoin du gros chiffre ; `Spec.compact` la ramène à 5 lignes pour que 6 indicateurs tiennent dans ~35 lignes de terminal.
- **Hauteur de terminal** : 7 indicateurs demandent ~40 lignes ; en dessous, les lignes à gros chiffre se compriment. Ne pas combiner hauteur proportionnelle et minimum sur les lignes empilées (constaté sur le Pi avec Textual) : utiliser des `Constraint::Min`/`Length` explicites dans ratatui.
- **Tests UI** : tester le rendu avec `ratatui::backend::TestBackend` à plusieurs hauteurs de terminal, pas seulement une grande.
- **Rust / portabilité** : remplacer `psutil` par la lecture directe de `/proc/stat` (CPU, deltas), `/proc/meminfo` (`MemAvailable`) et `cpufreq/scaling_cur_freq` ; racines `/sys` et `/proc` injectables pour tester sur Mac avec un faux arbre dans un répertoire temporaire.
- **Rust / cross-compilation Pi** : dépendances en Rust pur, aucune lib C ; cible `aarch64-unknown-linux-gnu` (Pi 5, OS 64 bits) via `cross` ou `cargo-zigbuild`.
- **Démo** : le mode démo implémente le même trait `Sensors` que les capteurs réels ; générateur pseudo-aléatoire maison (xorshift) pour éviter la dépendance `rand`.
- **Collecte / planification** : échéances calculées depuis un `Instant` de départ (`start + 500 ms × tick`), pas par addition de pauses, pour éviter la dérive ; l'attente est un `recv_timeout` sur un canal d'arrêt, donc l'arrêt est immédiat (pas de `sleep` à interrompre).
- **Collecte / panic** : le message d'un panic rattrapé dans le thread de collecte s'écrirait sur stderr en plein écran TUI ; `main` doit installer un hook de panic silencieux pendant que le terminal est en mode alterné.
- **CPU / `/proc/stat`** : la 1re lecture ne sert que de point de départ (indisponible). Un delta pris quelques ms après le démarrage ne porte que sur 1-2 jiffies de 10 ms, tous « actifs » : il donnait un faux pic à 100 % (constaté sur le Pi).
- **Hauteurs de lignes** : répartir les lignes restantes par cumul arrondi vers le bas (`split_heights`) et non avec `Constraint::Fill` : ratatui et Textual ne distribuent pas le reste au même endroit, et la ligne plus courte changeait de place par rapport à la version Python.
- **Service / dépendances** : `tiny_http` (threads, Rust pur) plutôt qu'Axum : pas de runtime async ni de dizaines de crates pour quelques clients à 1 Hz ; `serde_json` pour l'API et la sauvegarde ; `ctrlc` (feature `termination`) pour SIGINT/SIGTERM. Pas de SQLite : 48 h tiennent en mémoire (quelques Mo) et un snapshot suffit pour survivre à un redémarrage.
- **Service / testabilité** : le routage (`server::route`, `api::handle`) est une fonction pure testée sans socket ; les tests d'intégration (`tests/server.rs`, `tests/service.rs`) lient le port 0 et lisent le port réel.
- **Service / arrêt** : le thread d'acceptation de tiny_http libère le port avec un léger retard ; `Running::stop` attend la fermeture effective, sinon un redémarrage immédiat trouve « port déjà utilisé » (constaté : test intermittent en parallèle).
- **Sécurité / tunnel** : derrière un tunnel, toutes les requêtes viennent de 127.0.0.1 ; un filtre sur l'adresse source ne protège rien. Authentification applicative obligatoire (mot de passe en fichier 600, jamais en variable d'environnement visible dans `/proc`), limitation globale des échecs, comparaison en temps constant.
- **Historique / trous** : une période sans mesure est absente de la série (pas de `NaN` ni de 0) ; le rééchantillonnage ne comble pas les trous et garde les vrais min/max pour ne pas lisser les pics ; l'interface coupe la courbe au-delà de 2,5 pas.
- **Sauvegarde** : écriture dans un fichier temporaire puis `rename` (atomique) ; seulement les périodes terminées (la période en cours est rejouée après redémarrage) ; erreur d'écriture ou fichier corrompu = journalisé, jamais fatal. Compter environ 5 Mo par écriture, donc une écriture toutes les 10 min plutôt que chaque minute (carte SD).
- **Interface Web** : aucun CDN (le Pi est souvent sans Internet) ; pas d'`innerHTML` (les valeurs viennent du serveur) ; fonctions pures testées avec Node (`web/app.test.js`, lancé par `tests/web.rs`, ignoré si Node absent) ; tests de rendu faits à la main avec Playwright (ordinateur et téléphone). Le test de l'ontologie accepte aussi les fichiers `web/`.
- **Service / un seul dossier** : le mot de passe (`password`) et la sauvegarde (`history.json`) sont par défaut dans le dossier de l'exécutable (`current_exe()`), passé à `config::resolve` pour rester testable ; pas de `/etc`, `LoadCredential` ni `StateDirectory`. Déplacer le dossier déplace tout.
- **systemd** : utilisateur système `rpi-monitor` (créé par le script d'installation) + `SupplementaryGroups=video` (accès à `/dev/vcio` pour `vcgencmd`, donc pas de `PrivateDevices`) ; `ProtectSystem=strict` avec `ReadWritePaths=/opt/rpi-monitor` comme seul dossier inscriptible ; le port se règle par `Environment=` dans l'unité.
